# Mentor-pack conformance verification (ClaimGuardAI)

Phase-1 evidence for **rule correctness** (mentor weight 35/100): proof that our deterministic
engine produces exactly what the mentor pack's own strict scorer accepts, on every split it ships.

- Harness: `scripts/edu_conformance.py` (standard library only)
- Self-checks: `tests/edu_conformance/test_harness_selfcheck.py`
- Pack (read-only): `ClaimGuardAI_Student_Starter_Pack/ClaimGuardAI_Student_Starter_Pack`
- Oracle: `<pack>/src/evaluate.py` (the mentor's strict scorer, invoked as a subprocess)
- Reports: `<workdir>/<split>/{metrics.json,conformance.json}` (default workdir is the system
  temp dir; `C:/tmp/packout` was used for the runs recorded below)

## Methodology: two independent opinions

1. **The mentor's oracle** is executed verbatim:

   ```bash
   python <pack>/src/evaluate.py \
     --gold   <pack>/data/<split>/expected_results.jsonl \
     --pred   <predictions.jsonl> \
     --claims <pack>/data/<split>/claims.jsonl \
     --output <workdir>/<split>/metrics.json
   ```

   Non-zero exit is a hard failure and the scorer's own message is echoed into the report.
   The interpreter is `sys.executable` (the `uv run` venv), overridable with `--python`.

2. **An independent re-implementation of the admissibility contract** (no pack import) re-checks
   the same file: exactly 15 results per claim covering `R001..R015` once each; the exact 15-key
   result set; `status` / `severity` / `rule_version` (`1.0.0`) / `rule_source`
   (`fictional-rulebook/<RULE_ID>@1.0.0`) literals; `method`/`review_status`; non-empty evidence
   for every status except `NOT_IMPLEMENTED`; `confidence` null with `confidence_kind`
   `not_probabilistic`; `requires_human_review` true and non-empty `corrective_action` for
   `FAIL`/`UNABLE_TO_ASSESS`; `affected_line_ids` a subset of the claim's `line_id`s; every
   `{"path","value"}` evidence pair re-resolved by an RFC 6901 pointer walk against the
   **original** claim with type-exact equality (`true != 1`, `1 == 1.0`); the 17-key claim
   envelope; duplicate claim IDs, unknown claims and missing claim-rule pairs.

   It also **recomputes** `count/tp/fp/fn/status_accuracy/not_implemented` from gold+predictions
   and fails on any disagreement with the oracle's JSON, so a stale metrics file cannot pass.

Exit codes: `0` conformant, `1` non-conformant, `2` harness usage/IO error.

### The accuracy gate

`--min-accuracy` (default `1.0`) is applied to the **implemented** accuracy by default: exact
status agreement over the claim-rule pairs the predictor actually committed to
(`pred.status != NOT_IMPLEMENTED`).

Why not the raw `status_accuracy`: the pack counts `NOT_IMPLEMENTED` as wrong by design, so its
own accepted baseline sits at `status_accuracy 0.2 / not_implemented 4800`; gating the raw number
at 1.0 would reject the pack's own baseline. A file that commits to *nothing* is scored as 0.0, so
silence still fails. `--accuracy-scope total` gates on the oracle's raw `status_accuracy` instead,
and `--min-accuracy` < 0 disables the gate.

## Exact commands

```bash
# 1. The pack's own accepted baseline (self-check fixture; also regenerated by the tests)
uv run python ClaimGuardAI_Student_Starter_Pack/ClaimGuardAI_Student_Starter_Pack/src/run_baseline.py \
  --input  ClaimGuardAI_Student_Starter_Pack/ClaimGuardAI_Student_Starter_Pack/data/development/claims.jsonl \
  --output C:/tmp/packout/baseline_dev.jsonl

# 2. Harness against the pack baseline: MUST exit 0
uv run python scripts/edu_conformance.py --pred C:/tmp/packout/baseline_dev.jsonl --split development

# 3. All three splits (one predictions file per split via the {split} placeholder)
uv run python scripts/edu_conformance.py --pred 'C:/tmp/packout/edu_{split}.jsonl' --all

# 4. Strict gate on the raw oracle metric
uv run python scripts/edu_conformance.py --pred C:/tmp/packout/edu_dev.jsonl \
  --split development --accuracy-scope total --min-accuracy 1.0

# 5. Self-checks
uv run pytest tests/edu_conformance -q
```

## Independently verified vs taken from the pack

| Property | Where it comes from |
|---|---|
| Result admissibility (key set, literals, review flags, evidence presence, line-id bounds, evidence pointer resolution and value equality, per-claim rule coverage, duplicate/unknown claims) | **Verified independently** by the harness, twice over: the oracle also enforces it |
| Metric arithmetic (`count/tp/fp/fn/status_accuracy/not_implemented`) used by the harness | **Verified independently** by recomputation; disagreements fail the run |
| `issue_precision/recall/F1`, `false_alarm_rate`, `false_abstentions`, `missed_abstentions`, per-rule table, confusion list, `claims_with_all_statuses_correct` | **Taken from the oracle's JSON** (reported, not re-derived — only the subset above is cross-checked) |
| Gold status labels per claim-rule pair | **Taken from the pack** (`data/<split>/expected_results.jsonl`) — the ground truth for status correctness |
| Semantic rule behaviour (does R009 aggregate authorization quantity across lines? is R014's window the latest service date? …) | **Taken from the pack** — the harness checks *conformance*, not the rulebook's intent; see `docs/04_Rulebook.md` and the rule-level work in `claimguard/edu/rules/` |
| The claim data itself (envelopes, lines, coverage, authorizations, attachments) | **Taken from the pack** (`data/<split>/claims.jsonl`), read-only |

## Honest limitations

1. **The mentor's scorer is the oracle.** Its verdict is authoritative; the independent checks are
   a second opinion on admissibility and metric arithmetic, not a superior judgement. A
   systematically wrong engine that happens to reproduce the shipped labels would still pass.
2. **Evidence relevance is not proved.** The harness re-resolves each pointer against the original
   claim and demands exact equality of the value, exactly like the scorer. It cannot tell whether
   the cited field is *relevant* to the conclusion — that is the mentor's stated caveat
   ("Evidence-value checks do not prove that the chosen field is relevant", docs/07) and needs
   human review.
3. **Explanation quality is out of scope.** No check on whether the explanation text is correct,
   grounded or actionable; `prompts/explain_findings.md`,
   `exercises/llm_manual_scorecard.csv` and `exercises/llm_explanation_cases.jsonl` cover that
   manually. Explanation content is only required to be a non-empty string.
4. **Sibling outputs are snapshots.** The `claimguard/edu` numbers above were measured against the
   files present at verification time; re-run the harness after any engine change. The harness has
   no CI wiring — it is run manually and by the self-check tests.
5. **The harness is stricter than the oracle in a few contract-literal places** (`method`,
   `review_status`, `requires_human_review`/`corrective_action` typing, non-empty `explanation`,
   the 17-key envelope). A deviation there fails the run even though the oracle would accept it;
   those literals come from the frozen interface contract, not from the scorer.
6. **The gate metric is chosen deliberately.** `--min-accuracy 1.0` means "every status the engine
   committed to is exactly right", not "every claim-rule pair is implemented"; use
   `--accuracy-scope total` to require full coverage too. An all-`NOT_IMPLEMENTED` file is scored
   `0.0` and fails.
7. **Split selection is fixed** to the three shipped splits (`development|validation|stress`); the
   mentor's private 200 held-out claims (docs/07) are not reachable and cannot be substituted,
   which is exactly why an oracle-independent harness is the strongest available evidence today.

## CI behaviour and vendored fixtures

The mentor pack is delivered reference material: it is **not tracked in git** (`.gitignore`) and is
**excluded from the lint/type gates** (`[tool.ruff]` / `[tool.pyright]` in `pyproject.toml`), because
it ships its own formatting, its own tooling and its own `SHA256SUMS.json` manifest.

That splits the suite into two tiers, so CI stays honest and green:

| Tier | Needs the pack? | Where it runs |
|---|---|---|
| Engine logic and contract tests (`tests/edu`, 137 tests) | No — the rule catalogue is vendored | CI **and** locally |
| Pack-graded checks: gold-label replay and every harness self-check (`tests/edu_conformance`, 8 tests + 1 engine test) | Yes — gold labels and the strict scorer | Locally and as a pre-submission gate (`make edu-conformance`); they report **skipped** in CI |

The catalogue our engine needs is a 12 KB read-only input, so it is vendored verbatim under
`tests/edu/fixtures/pack_reference/` with checksums in `PROVENANCE.json`. Vendoring was verified:
running the engine against the vendored catalogue reproduces the same oracle result as running it
against the pack's own `rules/` directory (`status_accuracy 1.0000`, `fp 0`, `fn 0`).

**Consequence to state plainly:** CI green does *not* prove mentor-scorer conformance. The
oracle-graded run is a mandatory local step before any submission — `make edu-conformance` must be
part of the freeze checklist.
